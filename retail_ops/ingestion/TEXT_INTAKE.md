# 中文原文的批次接入

`batch_cli receive-document` 接收已登记的中文整理格式。一份文件可以包含多家门店、多个日期窗口和三类榜单。程序独立解析整份原文，逐项核对人工登记的门店身份、窗口、数据集与区块位置，全部通过后一次写入批次库。任何一项待核对时，本次不会留下部分通过的子批次。

每天上传的文件、登记快照及校验结果长期留存。查询仍按用户选择的首尾日期读取明确的发布版本，不保存每次查询。上传频率不改变报表窗口；每天获取的月累计报表仍保留原首尾日期。

## 字段与输入格式

业务字段名和字典中文定义不变。下表列出容易混淆的对应关系；其余映射沿用 [TEXT_SOURCE.md](TEXT_SOURCE.md) 的完整字段表。

| 现有字段 | 字典定义或现有用途 | 来源及使用位置 | 是否改名 |
|---|---|---|---|
| `transaction_amount` | 所选时间周期内，该账号所选择条件下门店的当天支付且当天未取消的订单用户实际支付金额 | 原文“成交金额”→ 店铺期间记录 → 查询及 RAC | 否 |
| `transaction_orders` | 所选时间周期内，该账号所选择条件下门店的当天支付且当天未取消的订单量 | 原文“成交订单量”→ 店铺期间记录 | 否 |
| `gross_revenue` | 商家的真实流水总额，包含商品原价、餐盒费；配送费是否包含依字典中的配送类型规则 | 字典已定义，当前数据集 schema 尚未接入；“营业额”待登记，不转为成交金额 | 否 |
| `sku_transaction_amount` | 所选门店、所选周期内，该 SKU 对应的成交金额 | 明确的商品金额榜，保留 SKU 排名 | 否 |
| `search_exposure_users` | 所选周期内，通过搜索列表看到商家的用户数 | 店铺指标“搜索曝光人数” | 否 |
| `search_term_exposure_times` | 所选窗口内来源记录中该搜索词的曝光次数 | 搜索词榜中“曝光次数” | 否 |
| `store_id`、`period_start`、`period_end`、`period_month` | 规范门店标识、报表首日与末日、完整自然月标签 | 原文门店和日期行，与独立登记核对 | 否 |

`manual_text_v2` 保留原来的完整自然月格式和已核对的简称。新登记的 `manual_text_v3` 是有明确标签的人工整理格式：

```text
店铺：B
时间范围2026-09-07至2026-09-07
成交金额100.50
成交订单量0
搜索曝光人数
top3交易商品成交金额：商品2026（成交金额100元），商品乙（成交金额20元），商品丙（成交金额5元）
```

这是合成格式示例，不是业务数据。首尾日均包含，跨月或跨年也写完整 `YYYY-MM-DD至YYYY-MM-DD`。不推断“昨天”“截至零点”或省略年份的日期。完整自然月的原文日期生成对应 `period_month`；其他窗口该字段为空。原 v1/v2 月度解析行为保留。

v3 的流量人数必须写完整“人数”标签；`搜索曝光` 等八个旧简称留给 v2。商品金额必须写 `商品名（成交金额100元）`，名称中带数字不会被当作金额的一部分。三类榜单仍分别使用已登记标题，各有完整三项；同名商品按原排名分别保存。缺失指标为空，明确的 `0` 保留，不用其他字段反推。

当前别名表继续列出 B–F。真实门店必须先完成独立身份对应和来源格式登记，不能从样例别名猜测真实后台门店。未知字段、标题、单位和别名会待核对，不因名称相似而落入现有分类。

## 独立登记

使用 `../contracts/intake_registry.v3.empty.json` 的空结构，按 `intake_registry.v3.schema.json` 填写并由可信操作人核对。它继续使用 `bindings` 和 `uploads`；CSV v1/v2 登记仍可使用。每个中文子数据集收据在既有字段之外声明：

| 接入元数据 | 用途 |
|---|---|
| `document_id` | 一次已核对的原文件接收标识，同文件各子收据使用同一值 |
| `source_block_line` | 原文件中相应“店铺”行的行号，从 1 开始 |
| `dataset_id` | 该区块中明确登记的店铺指标或榜单数据集，沿用现有名称 |
| `file_sha256` | 完整上传原文件的字节摘要；所有子收据一致 |
| `mapping_version` | 整份文件使用 `manual_text_v2` 或 `manual_text_v3`，不能混用 |
| `document_identity_evidence` | 程序从已核对的身份文件读取的原始字节包，供发布时重放整份登记；不是上传或模型可填的业务字段 |

每个实际出现的数据组都必须有且只有一个收据。门店指标组使用 `store_period_panel_metrics`；榜单分别使用 `demo2_top_search_terms`、`demo2_top_skus_by_sales_volume` 和 `demo2_top_skus_by_transaction_amount`。没有店铺指标行的榜单区块不产生店铺指标快照。缺少收据、额外收据或同一位置重复登记都不能部分接收。

`binding_id` 仍来自独立核对的账号、来源门店和规范门店对应关系；`source_page`、`extracted_at` 和日期不得由模型提议补造。可选 `aggregation_scope` 保留现有完整非日期筛选条件及时区声明，未知时省略。它是操作人核对记录，尚不等于美团后台认证。

登记和身份文件由可信操作人维护。模型可以提交现有格式的候选记录，但不能写这些核对文件。候选记录逐值对照独立解析结果；其中任何一项不一致，整份待核对。当前工具是本地 CLI，还没有提供面向非可信上传者的登录和权限管理。

## 留存、重试和修订

原始 UTF-8 字节完整保存，BOM 和换行形式不改写。原文、全部收据、所需身份记录和子批次结果在同一次 SQLite 事务中完成。解析、登记或修订检查失败时不会留下部分有效结果。重复接收返回原批次；修订使用新的文档和上传标识，显式指定各子数据集的前序批次，新版空值不会从旧版补回。

有效订单数、无效订单数沿用已有排除约定：若原文包含这两种标签，接入在创建数据库或保留原文前停止。请先准备符合既有约定的输入文件；程序不自动删行后把新字节称为原件。编码损坏、无法完成这项检查时同样不留存。

## 来源位置与发布

中文发布归档使用 `archive/<batch_id>/source.txt`；CSV 继续使用 `source.csv`。发布重新解析整份原文并核对所有区块登记，然后取明确选择的子批次。接收的完整性与发布选择分开：一份文档接收成功后，可以明确选择其中某些数据集或门店用于发布。

每行规范记录的 `source` 保留批次、文件摘要、来源页面和实际窗口。中文来源另有 `source_locator`：

| 定位字段 | 用途 |
|---|---|
| `locator_version` | 已登记的 `manual_text_locator_v1` |
| `source_block_line` | 门店区块起始行 |
| `store`、`window` | 原文门店行、日期行的片段 |
| `values` | 对应字段的原文片段，未提供的指标不伪造片段 |
| `item_ordinal` | 同一榜单行内第几项；店铺指标为 null |
| 片段中的 `line`、`column_start`、`column_end`、`text` | 原行号、从 1 开始的 Unicode 字符列、末端不含的结束列和原文片段 |
| `source_line_end` | 该记录所需原文证据的最后一行，不是中间 CSV 行号 |

行和列不包括 UTF-8 BOM 与换行符。多个榜单项可以来自同一行；商品主键仍含原排名。发布时重新核对片段及规范值；查询与区间 RAC 原样携带这些来源信息。

## 操作顺序

先准备并核对原文件、身份记录和全部收据。下列路径与标识必须替换成实际已核对的值；安装补丁不会导入你的文件。

```bash
.venv/bin/python -m retail_ops.ingestion.batch_cli receive-document \
  --database "$HOME/agent/meituan-intake/batches.sqlite3" \
  --registry "$HOME/agent/meituan-intake/reviewed_uploads.json" \
  --document-id 已核对的文档ID \
  --input /实际路径/已核对的中文原文.txt
```

成功响应中的 `batches` 提供各子批次 ID。按 [SOURCE_QUERY.md](SOURCE_QUERY.md) 将明确选择的 ID 发布为 `--source-records` 版本，再用 [RANGE_API.md](RANGE_API.md) 中的日期选择参数查询或运行 RAC。查询不重新上传、不创建发布版本，也不生成持久查询记录。

修订时另存一个 JSON 对象，将新文档中的 `upload_id` 映射到各自的前序 `batch_id`，通过 `--supersedes /实际路径/修订对应.json` 传入。只有已有同范围批次的子项需要指定前序。任一子项的前序不存在、范围不同或已有有效后继时，整份修订待核对。可选 `--proposals` 沿用规范候选数组，按实际原文组顺序逐值核对。

数据库结构仍为第 1 版，旧批次可以读取。当前代码与旧批次的处理规则摘要不一致时，发布会要求按新规则重新核对；旧字节和结果不会被覆盖。真实后台采集、任务调度和上传界面继续在此入口之上接入。
